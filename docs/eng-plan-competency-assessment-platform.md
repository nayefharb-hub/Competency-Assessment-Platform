## Stack (decided)

Fastest path, cloud-hosted, reversible (prototype-only call):
- **Next.js** (App Router, TypeScript) on **Vercel** — zero-config deploy.
- **Supabase** (hosted Postgres + Auth + Row-Level Security).
- **Recharts** for the dashboard.

Why: Supabase gives hosted Postgres + Auth (invite-only for the ~9 users) with
near-zero setup, and all DB access lives in Next.js server code — so the small
amount of access control this needs sits in one auditable server layer, not
per-route. Deep AI-training coverage → fast to build with Claude Code.
(Correction from review: Postgres RLS cannot hide columns by row-state; access
control is server-side — see below. RLS kept only as defense-in-depth ownership.)

Data-residency note: this puts KIB employee data on external cloud. Accepted for
the prototype pilot (founder's call). Mitigations: pseudonymize names for the
pilot and/or get informal IT sign-off. Supabase self-hosts later if the platform
needs it — the decision is not one-way.

## Data model

```
scale ─┐  APM 0–5; levels[] = {level, label, apm_text, kib_gloss}   (swappable row, NOT hardcoded)
       │
framework ─< competence_area (3: Perspective/People/Practice)
                 └─< competence_element (28: code, name, target_level)
                        └─< control (133: code, indicator, description, measures[],
                                     target_level, priority[H|M|L], active, reason, kib_note)
benchmark_profile (Intermediate now) ─< benchmark_target (apm_competence, level)  → re-points targets
app_user (email, name, role[assessee|assessor|admin])
assessment (assessee, assessor, cycle, profile, STATE, finalized_at)
   └─< score (control_id, self_level, assessor_level, assessor_touched, evidence)
   └─< target_snapshot (control_id, target_level)   ← frozen at approve (snapshot rule)
```

Notes:
- **Framework stored as data, not constants** (config-driven; required because the
  admin editor mutates it and the scale is swappable).
- **Two score columns for the prototype** — `self_level` and `assessor_level`
  (authoritative, shows in results). Deviation from the brief's 3-value
  Self/Manager/Agreed: the assessor's revision *is* the agreed value.
- `assessor_level` **defaults to `self_level`**; the assessor pass overrides deltas.
- `assessor_touched` flags whether the assessor actually reviewed/changed each
  control, so a blanket "Accept all" is distinguishable from genuine review (keeps
  the authoritative score, and the rollup, honest). Surface a review-coverage %.
- `measures[]` is reference-only (never scored).
- Inactive controls are stored (seed includes the 1 inactive) but excluded from
  every rollup.

## State machine (assessment loop)

```
 draft ──PM submits──▶ self_submitted ──assessor review──▶ APPROVED (locked)

 draft:          PM self-scores each active control (label picker; level-0 = "N/A / no
                 awareness" escape → 5 substantive rungs). PM is blind to target,
                 priority, reason, kib_note, and assessor_level.
 self_submitted: assessor sees self-scores; assessor_level pre-filled = self_level.
                 Assessor "Accept all" OR overrides specific controls (review-and-revise).
 APPROVED:      targets snapshotted; rollup computed; results revealed to PM;
                 self-vs-assessor gap preserved as signal. Record is locked/read-only.
```

Enforced by RLS + a state column, not by UI visibility alone.

## Access control (server-side, deliberately simple)

The flow is a straightforward **approve**, not an elaborate blind mechanism
(founder's call). Enforced in the Next.js server data layer — the service key
lives server-side only, the client never holds a table-capable key. RLS is kept
only as defense-in-depth row-ownership.

- **assessee (PM):** sees and edits only their *own* self-scores while
  `state = draft`. After submit, the assessment is with the assessor. Sees their
  final results only once the assessor has **approved**.
- **assessor (Head of PMO):** sees everything; edits values; approves — as-is or
  after editing — which snapshots targets and locks the record.
- **admin:** manages the tunable framework layer.
- **Targets are hidden from the PM during self-assessment** (brief methodology —
  stops them anchoring to the target), shown in results after approval. A one-line
  UI rule, not a column-security mechanism.

There is no separate "blind until agreed" machinery to build: the PM simply has no
view of the assessor's scoring, and the results page renders only once approved.

## Rollup engine (port faithfully from the workbook)

Authoritative spec = the Excel `Results`, `Scale`, `Framework` sheets.
- **Actual (per CE)** = mean of `assessor_level` across the CE's **active** controls.
- **Weakest control** shown alongside the mean (so one serious gap isn't averaged away).
- **Targets are not rolled up** — CE target = APM published value; where a CE spans
  two APM competences with different values, show the dominant value.
- **3-tier health:** Role Ready = actual ≥ CE target · Minor Gap = within half a
  level below · Capability Deficit = more than half a level below target OR any
  single control ≥ 2 levels below its own target.
- **Inactive controls contribute nothing**, regardless of any stored score.
- Snapshot targets at finalize so historic gaps don't shift if the profile changes.

## Results / dashboard (per design doc §Results)

Per-person: header · 3 area bars · bar-on-bar actual-vs-target (0–5) · gap list
sorted by gap size (CE, target, actual, weakest control, 3-tier status) ·
formula-driven narrative lines. **No radar. Numbers not percentages.** PMO view =
the 28-CE population rollup. Completion + median time-to-complete instrumented
per PM (feeds the design doc's assignment metric).

## Test plan (primary paths for /qa)

- **RLS / blind-until-agreed** (CRITICAL security) — assessee cannot see
  target/priority/reason/kib_note/assessor_level before APPROVED, via API not UI.
- **Auth allowlist** — listed email in, unlisted out.
- **Self-score submit** — draft→self_submitted; cannot edit after submit.
- **Review-and-revise + finalize** — accept-all path; override path; snapshot taken.
- **Rollup math** — mean, weakest control, inactive excluded, 3-tier thresholds,
  targets-not-rolled — all checked against the workbook's computed values.
- **Dashboard states** — zero results, partial (some controls unscored), full.

## Failure modes (new codepaths)

| Failure | Test? | Error handling? | Silent? |
|---|---|---|---|
| Server data layer returns targets/assessor scores to PM pre-approval | **must add (critical)** | column selection by state | would be SILENT → **critical gap** |
| Rollup includes an inactive control | must add | filter on active | silent wrong number → critical |
| Approve doesn't snapshot targets → historic gaps shift on profile change | must add | snapshot on approve | silent |
| Partial assessment → mean divides by wrong denominator | must add | count active-scored only | visible wrong % |
| Blanket "Accept all" masks non-review → authoritative score = untouched self-score | should add | `assessor_touched` + coverage % | silent credibility loss |

## Parallelization

depends on the schema+seed foundation (T0→T2→T3), and at one developer, schema
churn would break parallel lanes continuously. Build order:
**T0 → UX/UI design pass → T1 → T2 → T3 → T4 → T5 → T6 → T7 → (T8, T9) → T10.**
